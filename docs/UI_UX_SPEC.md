# UI_UX_SPEC.md
## Interface Specification for Izge

## UX goals
The UI should feel:
- serious,
- dark,
- structured,
- evidence-first,
- memorable,
- trustworthy,
- category-defining rather than generic.

## Product UX principle
Admins prepare and govern the memory.
Members contribute to and reason over it.

The UI should make that role split clear without turning the product into an admin-heavy enterprise console.

## Primary surfaces
- Landing / homepage
- Workspace dashboard
- Artifact contribution / upload screen
- Ingestion status view
- Signals view (contradictions / drift / next actions)
- Query interface
- Query result view
- Memory object detail view
- Graph / timeline view
- Admin user / permission view
- Audit / activity view

## Required result sections
- Direct Answer
- Why This Answer
- Supporting Evidence
- Related Decisions and Memory Objects
- Contradictions or Tensions
- Assumption Drift
- Recommended Next Actions
- Uncertainty / Missing Context

## Signals view expectations
The signals surface should show:
- active contradictions,
- active assumption drift,
- active next actions,
- urgency and uncertainty cues,
- concise grounded reasoning,
- drill-down paths into evidence and memory objects.

It should not feel like a generic analytics dashboard.

## Entry experience expectations
Members should understand:
- what they can ask,
- what kind of answers they will get,
- that the product is not freeform chat.

Admins should understand:
- what is in the workspace,
- what has been processed,
- whether the workspace is ready for reasoning/demo use.

## Visual direction
The interface should visually reinforce:
- traceability,
- contradiction as structural tension,
- drift as weakening continuity,
- guidance as a path forward.

Do not let the UI collapse into generic cards, generic AI assistant framing, or dashboard sludge.

## Final UX rule
The UI should communicate:
“This system reasons over your organization’s memory and helps you act on it.”
Not:
“This is just another AI chat box.”
