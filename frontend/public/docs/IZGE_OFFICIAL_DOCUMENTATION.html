Official Documentation

Izge

A local-first institutional memory and decision intelligence system for reconstructing organizational decisions, detecting contradictions and assumption drift, and producing evidence-backed next actions.

Version: implementation-aligned MVP Last updated: 2026-05-26 Standalone HTML No external assets
Primary rule: Izge is not generic search, chat over files, or generic AI SaaS. It is an inspectable memory system whose answers must remain grounded in artifacts, typed memory objects, graph relations, permissions, and provenance.

One-sentence definition

Izge reconstructs what an organization decided, why it decided it, what assumptions and constraints shaped the decision, what later contradicted it, what drifted, and what teams should do next.

Izge is not

  • internal search with a nicer interface
  • chat over files or generic RAG
  • a PM copilot that invents roadmap advice
  • a generic agent-memory framework
  • generic multi-tenant AI SaaS as the core product identity

1. Product contract

Memory before magicRaw documents are preserved, but typed memory and graph relations are the reasoning substrate.
Evidence before eloquenceEvery important answer should expose supporting artifacts, chunks, memory objects, and uncertainty.
Governance before speedPermissions, review status, and audit trails constrain every retrieval and answer surface.

Primary users

Admin

Prepares and governs the memory: uploads or reviews artifacts, manages users, inspects ingestion state, monitors signals, verifies readiness, and manages database/storage visibility.

Member

Contributes artifacts and asks evidence-backed questions. Members only see artifacts, evidence, signals, and derived outputs that their permissions allow.

Core use cases

  1. Decision lineage: explain what was decided, why, and which assumptions, constraints, outcomes, and commitments shaped it.
  2. Contradiction analysis: identify conflicts between old and new decisions, plans, commitments, or assumptions.
  3. Assumption drift: detect assumptions that have weakened, reversed, expired, or become unsupported by later evidence.
  4. Next-action guidance: recommend a grounded follow-up action based on unresolved memory tensions.
  5. Proactive ingestion: evaluate new artifacts against prior memory immediately after processing.
  6. Continuity and anti-duplication: surface prior relevant work before teams repeat work that already happened.

2. Core concepts

Workspace

The company or pilot boundary. Data, users, artifacts, memory objects, signals, jobs, and audit events are scoped to a workspace.

Artifact

A source document or pasted text item. It has a checksum, source type, visibility policy, review status, uploader, and immutable source bytes.

Artifact chunk

An ordered retrieval leaf under an artifact. Chunks support FTS retrieval and evidence selection but must be permission and review filtered before reasoning.

Memory object

A structured interpretation extracted from artifacts: Decision, Assumption, Constraint, Outcome, or Commitment.

Graph relation

A typed, evidence-aware relation between memory objects, such as BASED_ON, CONTRADICTS, or SUPERSEDES.

Signal

A durable proactive finding: contradiction, assumption drift, continuity overlap, supersession, or next action.

Query run

A persisted reasoning request with selected evidence, trace steps, stage runs, answer packet, and uncertainty notes.

Scenario run

A bounded impact-analysis packet over known memory. It identifies what to review; it does not forecast the future.

Orchestration job

A DB-backed asynchronous task with a bounded payload, lease, worker ownership, terminal result, and rejection path for unsafe requests.

3. System architecture

Izge is organized as layered product architecture rather than a monolithic chatbot. The interface calls FastAPI routes; application services enforce auth, permissions, evidence selection, graph reasoning, job management, and audit; persistence is SQLite plus filesystem artifact roots; optional LLM assistance is bounded behind local/private configuration flags.

High-level runtime architecture

The LLM is an optional assistance boundary. The database, graph, permissions, selected evidence, and verifier remain authoritative.

Backend layers

  1. Interface layer: app pages and admin/member flows.
  2. Application layer: API routing, sessions, roles, query lifecycle, signal surfacing.
  3. Intake layer: upload, paste, parse, chunk, ingestion state.
  4. Extraction layer: memory object creation with evidence spans.
  5. Graph layer: typed relationships, temporal continuity, contradictions, supersession.
  6. Reasoning layer: lineage, contradiction, drift, next action, scenario impact.
  7. Governance layer: permission filtering, review status, audit.
  8. Infrastructure layer: SQLite, filesystem, Docker, worker, local/private LLM gateway.

Frontend surfaces

  • Dashboard: operational workspace overview and active signals.
  • Artifacts / Ingestion: contribution, review, processing state.
  • Questions / Results: evidence-backed query workflow.
  • Graph: memory graph and temporal relationships.
  • Memory FS: logical memory organization and artifact roots.
  • Jobs: bounded orchestration stage catalog and queue visibility.
  • Readiness: PRD/website promise coverage mapped to evidence.
  • Data: database and artifact storage management.
  • Audit / Users: governance and role management.

The evidence substrate is Izge’s internal agentic file system. It is not a folder tree only; it is the combination of immutable source roots, ordered retrieval leaves, typed memory objects, graph links, signals, jobs, traces, and audit records.

What admins can inspect

Open /admin/data to see the Alembic revision, table row counts, SQLite path, storage roots, artifact physical paths, logical locators, checksums, size/existence checks, and safe metadata edit affordances.

Source immutability rule

Raw source content should not be edited in place. If a document changes, upload or paste a replacement artifact and reject, restrict, or annotate the old artifact. This preserves auditability and replayability.

5. Temporal knowledge graph

The graph is the core memory representation. It models institutional memory as related claims and evidence across time rather than as flat text snippets.

Domain model and graph links

Graph rules

  • Every non-trivial relation should remain explainable through source artifacts, chunks, or memory object evidence.
  • Contradiction and drift are modeled as relational phenomena, not as keyword overlap.
  • Temporal read models group claim occurrences and validity windows so teams can see how a belief changed over time.
  • Rejected or restricted evidence must not leak through graph summaries, signal details, or query results.

6. Bounded internal orchestration and worker daemon

Izge supports internal task division, but it is intentionally bounded. The orchestrator may divide a query or scenario into stages, but every stage receives a typed context packet and returns structured, cited output. It does not receive unrestricted database or filesystem authority.

Orchestration and DB-backed queue

Recommended stage catalog

  1. Orchestrator plan
  2. Evidence indexer
  3. Memory extractor
  4. Graph linker
  5. Contradiction interrogator
  6. Assumption drift interrogator
  7. Guidance planner
  8. Worker queue dispatcher
  9. Provenance verifier

Worker daemon

Run continuously when queued jobs should progress without manual API claim/complete calls:

scripts/orchestration-worker.sh --worker-id local-worker \
  --poll-interval-seconds 2 \
  --lease-seconds 120

Docker Compose starts the worker automatically as the worker service.

Authority boundary: stage packets must include selected artifact IDs, chunk IDs, memory IDs, omitted reasons, permission scope, review scope, output schema, max items, and uncertainty policy. Any job requesting trusted writes outside the result contract should be rejected.

7. AI and LLM boundary

Izge may use local/private LLM assistance, but AI output is not the authority of record. Deterministic storage, permission filtering, artifact review status, graph construction, signal classification, and provenance verification remain authoritative.

Allowed LLM assistance

  • Schema-validated memory extraction candidates.
  • Bounded query intent classification.
  • Answer wording from an already-selected evidence packet.
  • Signal explanation wording after deterministic signal detection.
  • Scenario lens classification across fixed templates.

Disallowed LLM authority

  • Inventing citations, artifact IDs, memory IDs, or hidden evidence.
  • Creating trusted graph edges without validation.
  • Overriding permission filters or review rejection.
  • Forecasting scenario outcomes as facts.
  • Persisting memory without a source artifact.

Local/private inference configuration

IZGE_LOCAL_LLM_ENABLED=true
IZGE_LOCAL_LLM_BASE_URL=http://127.0.0.1:11434
IZGE_LOCAL_LLM_MODEL=qwen3.5:4b
IZGE_LLM_QUERY_ROUTING_ENABLED=true
IZGE_LLM_ANSWER_SYNTHESIS_ENABLED=true
IZGE_LLM_SIGNAL_EXPLANATION_ENABLED=true

If the gateway fails, times out, returns malformed JSON, or fails schema validation, Izge must fall back to deterministic behavior and preserve the boundary in traces.

8. Security, governance, and trust

Authentication

Users sign in to a workspace. Role-aware APIs expose Admin and Member capabilities separately.

Permissions

Artifact visibility propagates into chunks, evidence refs, memory objects, signals, traces, graph views, and scenario runs.

Audit

Sign-ins, uploads, ingestion runs, query submissions, proactive signal generation, review updates, and permission changes are logged.

Permission-aware answer path

Governance failure condition: if Izge produces impressive answers but users cannot tell which evidence was used or whether restricted information leaked, the product has failed its trust contract.

  • Backend: http://localhost:8000
  • Services: backend, worker, frontend
  • Default local admin: admin@example.com / change-me-admin

python3 -m venv .venv
.venv/bin/pip install -e .

11. Evaluation and readiness gates

Izge should be judged by evidence, not by polished prose. The final test rule is simple: if the system produces eloquent nonsense, weakly justified contradictions, or uninspectable recommendations, it fails.

Core gates

# Backend compile
backend/.venv/bin/python -m compileall -q backend/app backend/manual_eval

# Seed/evidence/orchestration eval
cd backend
.venv/bin/python -m manual_eval.run_isolated_seed_eval

# Full synthetic company workflow
.venv/bin/python -m manual_eval.run_isolated_synthetic_company_workflow

Packaging and AI gates

# Docker-contained smoke
scripts/docker-smoke-eval.sh

# Worker daemon queue smoke
scripts/worker-smoke-eval.sh

# Ollama/local-private LLM smoke
scripts/ollama-smoke-eval.sh

# Frontend quality
cd frontend
npm run lint
npm run build

What the synthetic company workflow proves

  • Artifact ingestion and processing over one realistic company corpus.
  • Meaningful lineage, contradiction, drift, and next-action answers.
  • Memory FS organization and temporal knowledge graph projection.
  • Scenario replay and prompt-injection boundaries.
  • Member redaction of restricted evidence.
  • Rejected-artifact exclusion from trusted reasoning.
  • DB-backed orchestration job enqueue/claim/complete behavior.
  • Admin database/storage inspection and safe metadata update.

12. Company onboarding runbook

Create the workspace boundary.
Run one isolated workspace per company or pilot. Decide whether the deployment is local Docker, customer-hosted, EC2 pilot, or managed single-tenant.
Start the runtime.
Bring up backend, frontend, worker daemon, SQLite, artifact storage, and optional local/private LLM gateway.
Create or verify admin credentials.
Change default passwords before shared or production use.
Load source artifacts.
Upload Markdown, text, PDFs, or pasted notes that represent decisions, planning notes, status updates, reports, or postmortems.
Run ingestion.
Parse, chunk, extract typed memory objects, update graph relations, and generate proactive signals.
Review memory health.
Use Artifacts, Memory FS, Graph, Readiness, Data, and Audit to verify coverage and governance.
Ask locked-mode questions.
Use lineage, contradiction, assumption drift, and next-action queries. Inspect evidence, uncertainty, and trace steps.
Operate the memory.
Review or reject artifacts, upload replacements for changed documents, run backups, and keep migration checks green.

13. Roadmap, boundaries, and remaining risks

Implemented foundation

Portable MVP

React/FastAPI app, SQLite storage, artifact filesystem, memory extraction, graph, signals, traces, scenarios, Docker, worker daemon, DB inspection, and local LLM smoke path.

Production hardening

Next risk-reduction work

Worker metrics, dead-letter queue, retry/backoff policy, stronger multi-worker stress testing, deployment secret rotation, backups rehearsed in target environment.

Do not drift

Category guardrail

Avoid turning Izge into generic enterprise search, generic chat over documents, broad workflow automation, or fake multi-agent theater.

Future directions

  • Richer extraction quality metrics and larger gold corpora.
  • Explicit claim-family and claim-occurrence tables if the current temporal read model proves useful.
  • Additional company templates and industry-specific onboarding packs.
  • Optional edge-side lightweight inference, without making it required for MVP correctness.
  • More extensive deployment options for customer-controlled infrastructure.
